# Independent Scientific Verification Framework

## 1. Principles of Verification

A core design principle of NeuroGenesis AI is that **a language model must NEVER be permitted to assign verified status to its own output or to unverified computations.**

In scientific research, computation is not validation:
- An idealized computation (such as vacuum kinematics or numerical regression) is deterministic calculation, not physical proof.
- An independent verification requires a mathematically distinct, deterministically executed derivation or proof checker evaluating the output against declared physical invariants, exact boundary conditions, or closed-form analytical formulas.
- A model's critique or internal assertion of correctness is epistemic hypothesis, never proof.

## 2. Six Supported Epistemic Statuses

The platform rigorously classifies every claim, tool execution, and synthesis finding into one of six mutually exclusive statuses:

| Epistemic Status | Semantic Meaning | Visual Indicator | Verification Requirement |
| :--- | :--- | :--- | :--- |
| **`verified`** | Output verified by an independent deterministic checker in Rust using closed-form physical or exact mathematical derivation. | Green badge (`.pill-verified`) | `independently_checked = true`, max error $\le$ tolerance |
| **`calculated`** | Deterministic numerical or algorithmic output from a scientific tool. Correctly computed, but lacks an independent verification method or is an empirical fit. | Blue badge (`.pill-calculated`) | Valid tool execution, `independently_checked = false` |
| **`evidence_supported`** | Grounded in retrieved primary-source academic literature with persistent provenance (e.g. DOI, PMCID). | Purple badge (`.pill-evidence_supported`) | Valid source ID in investigation `sources` list |
| **`hypothesis`** | Conceptual claim, speculative inference, or reasoning generated by a model without empirical evidence or independent proof. | Amber badge (`.pill-hypothesis`) | Default status for model claims without proofs |
| **`uncertain`** | Execution failed, input parameters were non-finite, tool timed out, or verification could not be evaluated. | Gray badge (`.pill-uncertain`) | Execution error, timeout, or missing required fields |
| **`contradicted`** | Tool output directly violates known physical conservation laws, analytical boundary conditions, or independent derivations. | Red badge (`.pill-contradicted`) | Independent checker detected discrepancy $>$ tolerance |

Under no circumstances will a green `verified` badge be displayed for an unchecked calculation or an unverified model assertion.

## 3. Typed Verification Contract

Every verification check produces a structured `VerificationResult` persisted directly in SQLite and linked to the corresponding tool execution:

```rust
pub struct VerificationResult {
    pub id: String,                              // Unique UUID
    pub subject_id: String,                      // Associated tool or claim ID
    pub status: EpistemicStatus,                 // verified | calculated | ...
    pub method: String,                          // Description of verification method
    pub details: String,                         // Numerical results and comparison
    pub independently_checked: bool,             // True only if independently validated
    pub checker: Option<String>,                 // Rust checker identifier
    pub original_calculation: Option<Value>,     // Original Python worker output
    pub independently_calculated: Option<Value>, // Rust independent analytical result
    pub absolute_error: Option<f64>,             // max |actual - expected|
    pub relative_error: Option<f64>,             // relative discrepancy
    pub comparison_tolerance: Option<f64>,       // Floating-point or exact tolerance
    pub explanation: Option<String>,             // Mathematical and physical rationale
    pub verified_at: Option<String>,             // ISO 8601 UTC timestamp
}
```

## 4. Implemented Independent Checkers in Rust

The independent verification engine (`src/verification.rs`) operates natively in Rust, completely decoupled from the Python calculation worker and hosted language models.

### 4.1 Priority 1: Projectile Motion (`verify_projectile`)
- **Physical System:** Ideal classical kinematics under uniform gravitational acceleration in a vacuum over level terrain.
- **Analytical Formulas:**
  $$\text{Range } R = \frac{v^2 \sin(2\theta)}{g}$$
  $$\text{Time of flight } T = \frac{2v \sin\theta}{g}$$
  $$\text{Apex height } H = \frac{v^2 \sin^2\theta}{2g}$$
- **Input Validation:** Requires $v \ge 0$, $g > 0$, and finite angles $\theta$. Invalid parameters immediately trigger `EpistemicStatus::Contradicted`.
- **Boundary Conditions:**
  - $\theta = 0^\circ \implies R = 0, T = 0, H = 0$
  - $\theta = 90^\circ \implies R = 0, T = \frac{2v}{g}, H = \frac{v^2}{2g}$
- **Comparison:** Evaluates $|R_{act} - R_{exp}|$, $|T_{act} - T_{exp}|$, and $|H_{act} - H_{exp}|$. If max error $\le 10^{-6}$, marks `verified`; otherwise `contradicted`.

### 4.2 Priority 2: Arithmetic Validation (`verify_arithmetic`)
- **Operations:** Addition ($a+b$), subtraction ($a-b$), multiplication ($a \times b$), and division ($a/b$).
- **Precision:** Evaluates exact integer arithmetic where arguments are integral; evaluates floating-point comparisons with tolerance $10^{-9}$.
- **Singularity Handling:** Division by zero is detected; if the worker returns an error or non-finite result, status is `uncertain`; if the worker claims a finite result for division by zero, status is `contradicted`.

### 4.3 Priority 3: Descriptive Statistics (`verify_statistics`)
- **Metrics Verified:**
  - Sample mean: $\bar{x} = \frac{1}{N}\sum_{i=1}^N x_i$
  - Bessel-corrected sample standard deviation: $s = \sqrt{\frac{1}{N-1}\sum_{i=1}^N (x_i - \bar{x})^2}$
  - Extremities: $\min(x)$, $\max(x)$
  - Sample size: $N$
- **Validation:** Minimum sample size $N \ge 2$ for sample variance/stdev. Checks against float tolerance $10^{-6}$.

### 4.4 Priority 4: Power-Law Fitting Consistency Check (`verify_power_law`)
- **Theoretical Basis:** Empirical power-law fitting ($y = a x^b$) via log-transformed least-squares regression ($\ln y = \ln a + b \ln x$) is an empirical estimation, not an exact analytical ground truth.
- **Verification Rule:** A statistical fit must **never** be labeled `verified` simply because the regression ran without error.
- **Independent Consistency Check:** The Rust checker verifies that the fitted parameters satisfy the least-squares normal equations:
  $$\sum_{i=1}^N e_i = \sum_{i=1}^N (\ln y_i - \ln a - b \ln x_i) \approx 0$$
  $$\sum_{i=1}^N (\ln x_i) e_i \approx 0$$
- **Outcome:**
  - If the normal equations are satisfied within tolerance: the result retains **`EpistemicStatus::Calculated`** with `independently_checked = false`.
  - If the worker produces non-physical, non-finite parameters, or violates the normal equations: the result is marked **`EpistemicStatus::Contradicted`**.

## 5. Unsupported Verification Cases

When a calculation or claim cannot be verified independently:
1. **Unregistered Tools:** Fallback to `verify_unsupported()`, which retains `EpistemicStatus::Calculated` with `independently_checked = false`.
2. **Generative Model Claims:** Specialist claims and synthesis assertions without source citations or verified calculations are strictly assigned `EpistemicStatus::Hypothesis`.
3. **Formal Verification (Lean):** Lean 4 theorem proving is designed as an external verification extension point and is not active in Milestone 1.2.1.
